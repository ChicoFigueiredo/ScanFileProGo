## What gets signed

Only one artifact: `scanfile.exe`, the Windows x64 executable produced by the
release pipeline. Nothing else is submitted for signing — no installers, no
scripts, no third-party binaries.

## How artifacts are built

Every signed binary is produced by GitHub Actions, from this repository, and
never from a developer workstation.

- Workflow: [`.github/workflows/ci-cd.yml`](../.github/workflows/ci-cd.yml)
- Trigger: a push to `main` or a `v*` tag
- Runner: GitHub-hosted `windows-latest`
- Toolchain: the Go version pinned in [`go.mod`](../go.mod)
- Build: `go build` with the release version injected via `-ldflags`
- Resources: `VERSIONINFO` and the application manifest are generated by
  [`go-winres`](https://github.com/tc-hib/go-winres) from
  [`winres/winres.json`](../winres/winres.json), so every signed binary carries
  product name, company, copyright and a version that matches the release tag.
  The pipeline **fails** if any of those fields is empty or if the resource
  version does not match the release version.

Before a binary can be built, the same workflow must pass:

- `go vet ./...`
- `go test -race ./...` — the full suite, with the race detector
- `node --test "ui/tests/**/*.test.mjs"` — the interface test suite

The signing request is submitted by the
`signpath/github-action-submit-signing-request` action, using the artifact
uploaded by the same workflow run. No human uploads a binary to SignPath by hand.

## Approval process

1. Changes reach `main` through a pull request.
2. A push to `main` or a version tag starts the pipeline.
3. Static analysis and the full test suite must pass; a failure stops the run
   before any binary is produced.
4. The signing request is created automatically by the pipeline and reviewed in
   SignPath by the Approver named above, who verifies that the run corresponds
   to an intended release commit.
5. The signed binary is attached to the GitHub Release, together with its
   SHA-256 checksum. The checksum is computed **after** signing, so it covers
   the signed file.

## Security measures

- Multi-factor authentication is required on GitHub and on SignPath for every
  account with access.
- Signing credentials exist only as GitHub Actions secrets, scoped to this
  repository. They are never present on a developer machine.
- The private key never leaves SignPath's HSM. This project has no copy of it.
- The pipeline is skipped entirely when the SignPath secrets are absent, so a
  fork cannot produce a signed binary.
- Release artifacts are published only through GitHub Releases.

## Reporting a problem

Suspected abuse of the signature, a compromised release, or a binary that claims
to be ScanFile Pro and is not: open an issue at
<https://github.com/ChicoFigueiredo/ScanFileProGo/issues>, or write to the
maintainer through the contact on the GitHub profile. Reports of a suspected
compromise are investigated before any further release is signed, and the
certificate holder is notified so the certificate can be revoked if warranted.
